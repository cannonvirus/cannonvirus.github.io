# 레이아웃·태그·보고서형 개편안 (2026-10-17)

브랜치 `design/layout-tags-20261017`의 변경 설명입니다. 이 문서는 시안이며 `main`에는 아직 반영하지 않았습니다.
보고서형 글의 문체는 별도 작업에서 정하므로 이 문서는 화면 형식만 다룹니다.
글 화면의 구조는 사용자가 지정한 레퍼런스(claude.dev 블로그 "How the Claude Code team does code review")를 기준으로 했습니다.
레퍼런스의 코드·글꼴 파일·디자인은 복제하지 않았고 구조와 동작 원리만 참고했습니다. 분석은 7절에 있습니다.

## 1. 현황 (2026-10-17, main 820c31d 기준)

| 항목 | 값 |
| --- | --- |
| 글 수 | Projects 12편(VISER 6, 보드게임 AI 6), News 14편(W38~W41) |
| 사용 중인 태그 | 16개 |
| 1편짜리 태그 | 7개(44%): agent-eval, eng-practice, model-release, model-training, multi-agent, prompt-context, robotics |
| 2편 이상 태그 | agent-platform 2, agent-skills 2, image-video-gen 2, rag-retrieval 2, coding-agent 3, vlm 3, inference-cost 4, game-ai 6, VISER 6 |
| 목록에만 있고 쓰이지 않은 태그 | autonomous-research, model-serving (VISER `blog_tags.TAGS` 16개 중 2개) |
| 글당 태그 수 | News 평균 1.6개(최대 3개), Projects 1개(연재 이름) |

### 1.1 태그의 문제

1. 축이 섞여 있습니다. Projects는 연재 이름(`VISER`, `game-ai`)을, News는 주제(`vlm`, `inference-cost`)를 태그로 씁니다.
   태그 목록 한 화면에 프로젝트 이름과 기술 분야가 함께 나옵니다.
2. 이름이 영문 약어입니다. `eng-practice`, `prompt-context`, `inference-cost`는 이름만으로 범위를 알기 어렵습니다.
3. 분류가 글 수에 비해 세분되어 있습니다. 태그 7개가 글 1편에만 붙어 있어 태그를 눌러도 같은 글 1편만 나옵니다.
4. 대소문자가 섞여 있습니다(`VISER`와 나머지 소문자).
5. 태그 페이지는 영문 이름의 알파벳순 목록이고 설명이 없습니다.

### 1.2 레이아웃의 문제

1. 첫 화면은 두 구역의 글을 날짜순 한 목록으로 보입니다. News 글은 날짜가 앞서 둘째 페이지부터 나옵니다.
2. Projects 목록에서 두 연재의 글이 날짜순으로 섞입니다. 글 끝의 이전·다음 글도 연재와 무관하게 이어집니다.
3. 본문 전체가 고정폭 글꼴(Fira Code)이라 긴 한글 문단에서 영문·숫자 구간의 글자 폭이 넓습니다.
4. `style.css`의 `word-break: keep-all`이 적용되지 않았습니다. 테마가 모든 요소에 `word-break: break-word`를 직접 지정하기 때문입니다.
   390px 화면에서 "올라 / 가는"처럼 낱말 중간에서 줄이 바뀌었습니다.
5. 인쇄 색이 없습니다. 브라우저 기본값(배경 그래픽 끔)으로 인쇄하면 흰 종이에 밝은 회색 글자가 나오고 여백이 없습니다.
6. 684px 이하에서 메뉴가 "Menu ▾" 펼침 단추로 바뀝니다. 메뉴 항목은 4개라 한 줄에 들어갑니다.

### 2.4 글 수 분포 목표

- 분야 태그 수는 글 30편까지 6~8개로 둡니다. 개편 후 7개입니다.
- 새 분야는 해당 글이 2편 이상일 때만 만듭니다. 개편 후 1편짜리 태그는 0개입니다(이전 7개, 44%).
- 글당 분야 태그는 1~2개입니다. 첫째 태그가 글의 중심 분야입니다.
- 분기마다 1편짜리 태그를 확인하고, 2분기 연속 1편이면 가까운 분야로 합칩니다.
- 한 분야가 전체 글의 40%를 넘으면 나눌지 검토합니다.

## 4. 보고서형 글 형식

### 4.1 적용 방법

- 템플릿: `layouts/_default/report.html`
- 글 하나에 적용: 머리말에 `layout: report`
- 구역 전체에 적용: `hugo.yaml`에 아래를 추가합니다. 제안은 News 전체 적용, Projects는 글마다 선택입니다.

```yaml
cascade:
  - target:
      path: "{/news/**}"
    layout: report
```

구역 페이지의 `type`이 `posts`라 `layouts/news/` 같은 구역 이름 폴더는 Hugo가 고르지 않습니다(이 브랜치에서 확인).
그래서 구역별 목록은 `_default/list.html`이 부분 템플릿을 고르는 방식으로 만들었습니다.

### 4.2 구성 순서

| 순서 | 요소 | 내용 | 자료 출처 |

| 1 | 분류 줄 | News: "News · 주간 기술 정리 2026-W40". Projects: "VISER 개발일지" | 구역, 주차, 연재 |

### 4.3 화면 기준

- 폭: 목록 페이지는 테마 폭(864px) 그대로입니다. 글 페이지는 1,100px 이상에서 1,180px까지 넓혀 옆 목차를 둡니다(`.container:has(.has-rail)`). 1,280px과 390px에서 가로 넘침이 없는 것을 확인했습니다.
- 색: 테마 색 변수(`--accent`, `--foreground`)만 씁니다. 인쇄에서는 `style.css`의 인쇄 규칙이 색 변수를 흰 바탕용으로 바꿉니다.
- 인쇄: 그래프 PNG는 어두운 바탕 그대로 인쇄됩니다. 인쇄용 밝은 그래프는 이 시안 범위 밖입니다.

### 4.4 사용자 결정이 필요한 항목

1. 글꼴 변경(L7) 여부. 본문이 Pretendard로 바뀌어 터미널 테마의 인상이 줄어듭니다. 메뉴·목차·절 제목은 고정폭으로 남습니다.
2. News 전체에 보고서형을 기본 적용할지, 글마다 고를지.
3. 보고서형에서 본문 첫머리 안내 인용(원문·뉴스레터)을 숨길지. 문서 정보와 내용이 겹칩니다. 시안은 남겨 두었습니다.
4. `key_points`를 VISER가 만들지, 본문 `==강조==` 문장으로 대신할지. 강조 문장은 앞뒤 문맥 없이 읽으면 뜻이 불완전한 경우가 있습니다(예: Shopify 글 "사람끼리의 일치도가 판정 모델이 닿을 수 있는 상한이다").
5. Projects에 분야 태그를 붙일지. 시안은 연재만 둡니다.
6. 리드 문장 굵게(L17)를 쓸지와 쓰는 방법. 화면은 `**문장**`만 있으면 동작합니다. 개발일지는 글쓴이가, 주간 보고서는 VISER 프롬프트가 넣어야 합니다. 문체 규칙(문단마다 쓰는지, 편당 몇 개인지)은 문체 작업 결과를 따릅니다.
7. 레퍼런스처럼 밝은 바탕으로 바꿀지. 시안은 어두운 바탕을 유지했습니다. 그래프 PNG가 어두운 바탕용 색으로 그려져 있어(`docs/weekly.md` "그래프는 블로그의 어두운 바탕과 같은 색") 바탕을 바꾸면 그래프 색도 다시 정해야 합니다.
6. 기존 News 14편의 태그를 바꾸는 방법(5절 2단계).

## 5. 적용 순서

1. 이 브랜치를 `main`에 병합하고 푸시합니다. 태그 이전 전에도 화면이 동작합니다.
   이전 태그는 이름표 파일이 없어 영문 이름 그대로 보이고, 연재가 없는 Projects 글은 목록 아래 카드 형식으로 보입니다(이 브랜치를 그대로 빌드해 확인).
2. 머리말 변환. `python docs/design-20261017-migrate.py content`로 바뀔 내용을 출력해 확인한 뒤 `--write`로 씁니다.
   - Projects 12편은 블로그 글이므로 이 단계에서 바꿉니다.
   - News 14편은 README의 "손으로 고치지 않는다" 규칙의 대상입니다. 둘 중 하나를 사용자가 정합니다.
     (가) VISER 변경(2.5절) 후 해당 주차를 다시 게시해 VISER가 새 태그로 다시 씁니다. 체크가 풀린 글은 다시 쓰이지 않습니다.
     (나) 이번 한 번만 이 스크립트로 머리말 `tags` 줄만 바꿉니다. 본문은 바꾸지 않습니다.
3. VISER의 `blog_tags`·`blog_export`를 2.5절대로 바꾸고 고정 표본으로 평가합니다. 이 단계 전에 게시한 글은 이전 이름을 쓰므로 2단계와 같은 날 처리합니다.
4. 보고서형을 적용합니다(4.1절 cascade). 문체 작업 결과가 나온 뒤 `key_points` 생성을 붙입니다.
5. 2단계 뒤 이전 태그 주소(`/tags/vlm/` 등)는 사라집니다. 외부에서 이 주소로 연결된 곳은 미확인입니다. 필요하면 새 태그의 `_index.md`에 `aliases`로 이전 주소를 넣습니다.

## 6. 되돌리는 방법

- 병합 전: 브랜치를 지우면 됩니다. `main`은 바뀌지 않습니다.
- 병합 후: 병합 커밋을 `git revert -m 1 <병합 커밋>`으로 되돌립니다. 레이아웃·CSS·`hugo.yaml`·`content/tags`·`content/series`가 이전 상태로 돌아갑니다.
- 머리말 변환 후: 변환 커밋을 따로 두고 그 커밋만 `git revert`합니다. 레이아웃 변경과 섞지 않습니다.
- 보고서형만 끄기: `hugo.yaml`의 cascade 항목을 지웁니다. 머리말에 `layout: report`를 적은 글은 그 줄을 지웁니다.
- 본문 글꼴만 되돌리기: `style.css`의 "글꼴 구분" 규칙 묶음(`--body-font`를 쓰는 선택자 목록)을 지우고 `extended_head.html`의 Pretendard 줄을 지웁니다.
- 옆 목차·진행률만 끄기: `_default/single.html`과 `report.html`에서 `post-rail.html` 호출을 지우고 `extended_footer.html`의 `reading.js` 줄을 지웁니다. 목차는 본문 위 상자(`toc-inline.html`)로 남지만 넓은 화면에서 숨겨지므로 `style.css`의 `.toc-inline { display: none; }`도 지웁니다.
